一、問題回溯：為什麼線上版沒有中文翻譯？

使用者反饋在進入首頁並點選 #/song/1 (Color) 與 #/song/2 (幻想曲WONDERLAND) 時，畫面僅有日文歌詞與應援標記，中文翻譯區塊為空。

關鍵根因分析：LRCLIB Fallback 與客戶端 LocalStorage 快取陷阱
  1. 外部網路與 Worker 延遲或被擋： 網站原本依賴客戶端向 Cloudflare Worker (iris-lyrics.jonathanhrlin.workers.dev) 發起網易雲 API 代理請求。若冷啟動延遲、逾時或被風控，程式碼會自動 fallback 至開源歌詞服務 lrclib.net。
  2. LRCLIB 缺乏中文歌詞： LRCLIB 僅收錄同步日文原文，回傳物件的 z 欄位為空字串 ""。
  3. 永久快取毒化（Cache Poisoning）： 前端一旦自 LRCLIB 取得歌詞，便將該物件寫入使用者的 localStorage['iris-ft-lyrics']。隨後程式中設定了防重複載入保護：if (!k && (n in LY || AF[n])) return;。這導致一旦使用者的裝置抓過一次 LRCLIB，本地便永遠留存「無中文版本」，無論重整幾次都不會再獲取中文！
  4. 缺乏靜態預置（Baked Data）： 網站原本在 BK 中預建了應援時間碼（call_times.json），但歌詞 LY 卻完全留空（LY={}），形成 100% 依賴客戶端即時網路的單點故障風險。

二、架構借鏡：watain666/Vaundy-Taiwan-2026 的最佳實踐

參考 watain666/Vaundy-Taiwan-2026（台北場應援指南）的設計哲學：

  • 資料預建化（Data Pre-baking）： 在 src/song-lyrics.js 與 data.js 中將所有曲目的完整日文歌詞、羅馬音、漢字注音以及繁體中文精譯直接作為專案文檔持久化儲存。
  • 離線第一（Offline First）： 使用者第一次打開頁面時不需要即時仰賴第三方音樂 API（網易雲、LRCLIB），杜絕了網路連線波動與 API 變更引發的故障。
  • 尊重使用者自訂： 若使用者透過介面手動編輯或上傳 LRC，再儲存至本地覆蓋；預設情況下則永遠提供官方最高品質的精校版本。

四、工程落實：程式碼改造與舊快取自愈機制

3 建立 Baked 資料庫與客戶端自動修復

我們在 _src/baked_lyrics.json 建立了包含全部 25 首歌曲的離線資料文檔，並於 _src/portal.py 注入前端：

// 於 HTML 初始化時注入 BKL = __BKL__
var S = __S__, BK = __T__, BKL = __BKL__;
try {
  LO = JSON.parse(localStorage.getItem(K)) || {};
  LY = JSON.parse(localStorage.getItem(KL)) || {};

  // 【核心自愈邏輯】：
  // 遍歷預置庫。若使用者過去曾經造訪過、被 LRCLIB 污染導致無中文（!LY[bk].z.some(...)），
  // 或尚未有該曲，自動以精校高品質的 BKL 覆蓋修復！
  for (var bk in BKL) {
    if (!LY[bk] || !LY[bk].z || !LY[bk].z.some(function(x) { return !!x; })) {
      LY[bk] = BKL[bk];
    }
  }
} catch(e) {}
自愈機制帶來的優勢
  • 舊訪客無痛升級： 曾進入過網站、localStorage 殘留 LRCLIB 空中文資料的舊訪客，重新打開網站即時自動修復，無需手動清除快取。
  • 新訪客秒開載入： 進入任何歌曲頁面首屏立即渲染完整日文與繁中歌詞，完全不需要等待 Cloudflare Worker 或 LRCLIB 網路延遲。
  • 完整保留自由度： 使用者依然可以使用「歌詞管理」或「編輯歌詞」手動覆蓋或重新搜尋。

五、自動化建置與 GitHub 推送

完成程式碼更新後，依序執行了以下自動化驗證與部署步驟：
